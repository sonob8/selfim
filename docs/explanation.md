# Explanation: なぜ2論文を統合するのか

このシステムは「SIM/CRSI」(論文A)と「Self-Harness統合フレームワーク」(論文B)という立場の異なる2本の論文を、役割を分けて組み合わせています。論文Aは改善の**記憶**を設計し、論文Bは改善の**実行制御**を設計しています。どちらか片方だけには、実運用で効く弱点があります。

## 論文Aだけだと何が起きるか

SIM/CRSIは「根原因ごとに試行をグループ化したDB」を提示します。これがあれば、なぜその編集をしたのか・何を期待したのか・実際はどうだったのかが後から参照できます。ただし論文Aのループ自体には、編集の形状に対する制約がほとんどありません。候補はハーネス全体に及び得ます。

論文Bが示した実験知見はここを突いています。ハーネス全体を一度に書き換えると、出力フィルタが検証フックが読むべきスタックトレースを削るように、モジュール間の共有状態仮定が壊れます。全文書き換え方式はトークン消費も約10倍に膨らみました。つまりSIMの記憶をどれだけ丁寧に作っても、編集の適用方式が粗いとゲートなしの探索は遅く壊れやすいのです。

## 論文Bだけだと何が起きるか

論文Bの4段階ループ(Diagnose→Propose→Validate&Filter→Deploy)は実行制御として堅牢です。モジュールを1つずつ直し、構文・実行・非退行・予算のゲートを通します。しかし純粋な論文B方式では、過去の改善がハーネスのコードにしか残りません。編集が後のラウンドで置き換えられたり削除されたりすると、その試行が「何を予測し、なぜ外れたのか」という証拠は消えます。論文Aが図解した失敗パターンはまさにこれです。SIMなしの継続実行は、継承されたゲートの目的を知らずに同じ箇所を何度も直し、デッドロックを2回修復する羽目になりました。

## 統合: 記憶と実行制御の分離

本システムの分担は次のとおりです。

| 責務 | 担当 | 出典 |
|---|---|---|
| 編集を1候補1モジュールに限定 | ModuleRegistry | 論文B Safe Guard 1 |
| 繰り返し失敗クラスタへの紐付けを必須化 | Evaluator.cluster_failures | 論文B §III |
| 構文・実行・非退行・行数予算のゲート | ValidationGate | 論文B Safe Guard 3 |
| 評価データ・ログを書込スコープ外へ | run ワークスペース構造 | 論文B Table III |
| 根原因×試行履歴のDB | SIMManager | 論文A §3.2, D.3 |
| 予測を評価前に記録し評価後に検証 | record_predicted / record_outcome | 論文A §3.2 |
| 採択候補のみ記録、不採択はSIM不変 | MainLoop の更新規則 | 論文A §3.2 |
| SIM全文を提案と選択に渡す | render_for_prompt | 論文A §3.2 |

この分担の結果、「小さく検証された編集」が「証拠つきで記憶される」ループになります。

## 個別の設計判断

### ジャッジにルーブリックを渡す(Ground Truthなし)

タスクが「裁判の判断」「人事評価」のような推論タスクのため、正解の有無で採点できません。ユーザー提供のルーブリック criteria に重みを付けてLLMジャッジが採点します。数値スコアだけでなく `missing_points`(何が不足していたか)を必ず出させるのは、Proposerへの入力を「低い点数」ではなく「具体的な欠落」にするためです。論文Bの知見では、スカラー値しか見ないオプティマイザは探索が進まないことが確認されています。

### 単発の失敗を編集対象にしない

1つの失敗rolloutには偶発的なミスが混ざります。これに反応してルールを追記し続けると、起きなかった失敗への防止規則が蓄積します(論文Bが "Phantom Guardrails" として警告するパターン)。Evaluatorはエラー署名でクラスタリングし、`count == 1` のクラスタをProposerに渡しません。

### ハーネス欠陥とモデル限界の切り分けをトレースに含める

改善対象はハーネスであってモデルではありません。モデルの知識不足で失敗しているタスクにハーネス編集を投げるのは計算の無駄です。ジャッジに `attribution`(`harness` / `model`)を出させ、`model` クラスタは編集対象から除外します。

### モデルプロバイダの抽象化とMockModel

本プロジェクトの運用はBedrockが最終形ですが、開発環境にはAPIキーがありません。`build_model(role, provider)` でプロバイダを差し替えられる構造にし、`MockModel` が決定的応答を返すことで、テストとチュートリアルをキーなしで実行できます。ロジック(SIM更新・ゲート判定・スクリーニング規則)の正しさと、LLM応答の質は別の問題であり、前者はMockModelで検証します。

### 予測を「評価前に」記録する理由

事後的に「この編集はこう効いた」と書くと、結果を知った後の説明にならず、精度の検証ができません。`record_predicted` で先に予測を固定し、`record_outcome` で `fixed`/`missed` を埋める2段階に分けることで、「予測がどれだけ外れたか」が履歴として残ります。この証拠が、SIMの8原則にある「テスト済みの方向は新エビデンスがある時だけ再訪」の判断材料になります。

## 残した限界

- ジャッジのスコアはLLMの判断に依存するため、同一ハーネスでも実行間で変動します。5rolloutの平均で抑えていますが、差が1点以内の採択判断はノイズを含みます
- SIM全文をプロンプトに渡す方式は、エントリが数百に達するとコンテキスト上限に当たります。論文Aはこの方式を明示的に選んでおり(検索による見落としを避ける)、本実装もそれに従います。長期運用では要約の検討が必要です
- ValidationGateの「新コードパスに到達したことの確認」は、本実装では実行時計測(モジュール呼び出しの記録)で行います。到達しないままスコアだけ上がる候補は、偶発的な改善の可能性があり、記録されても信頼できません
